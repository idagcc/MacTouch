# Open source options for MacTouch

Checked 31 October 2026. The best references are **Touch-Up and its TouchUpCore framework** for touchscreen behavior, **HIDAPI** for portable hardware access, and **hidapitester** for independent hardware diagnostics. MacTouch can keep its current native Swift and IOKit implementation while adopting specific, reviewed techniques. Adding a general USB library alone will not solve report decoding, monitor mapping or gestures.

HIDAPI's license choice is meaningful: it offers a permissive BSD-style option explicitly. Conversely, a GitHub “Other” license badge is not enough to classify a library. libuiohook's source headers and separate LGPL file establish its LGPL terms even though its main COPYING file contains the incorporated GPL text. Any actual source adaptation should retain the relevant copyright/license notices and identify the pinned revision. Review LGPL/GPL obligations before bundling those components; keeping an independent diagnostic tool outside the app avoids making it a production dependency.

## What TouchUpCore actually does

The current Touch-Up input layer is an 834-line C implementation. It walks IOKit's parsed HID element collections, caches element values and drains an `IOHIDQueue`. Its current version stores state per HID device and chooses the interface with the most contact collections when several interfaces share a USB location. For hybrid devices it tracks total contact count and a running offset before marking a frame complete. [Pinned HIDInterpreter.c](https://github.com/shueber/Touch-Up/blob/59a4fd28ae939dafb2f4ad9df9b00e959b40eada/TouchUpCore/HIDInterpreter.c)

That is valuable implementation experience, but not a small parser library to drop into the Swift package. In particular, its queue callback treats an empty value queue as a report boundary. Our report-callback architecture already has explicit report boundaries and should retain that advantage. The safer extension is a bounded frame assembler around the existing decoder, with independent state per device, report-ID tracking, count validation, timeout reset and fixtures for partial frames. This is the recommended adaptation of the protocol approach, not a claim that the upstream code is a verified replacement.

Touch-Up's pinch output uses numeric event type `29` and numeric fields including `113`, `114`, `116`, `118` and `132`. These are not the documented Quartz mouse/scroll constructors used by MacTouch. Importing the framework wholesale would also import that compatibility assumption. Keep public mouse/scroll output and review advanced gesture output separately. [Pinned cursor utilities, lines 219 onward](https://github.com/shueber/Touch-Up/blob/59a4fd28ae939dafb2f4ad9df9b00e959b40eada/TouchUpCore/TUCCursorUtilities.m#L219)

## The small compatibility improvement worth adopting

TouchMyMac adds a focused initialization step: find an advertised HID **Feature** element on Digitizers page `0x0D`, Device Mode usage `0x52`, and write multi-input mode `2` through public `IOHIDDeviceSetValue`. This can help a controller that starts in single-pointer emulation. Its implementation also performs vendor certification-feature reads, which should not be generalized without controller evidence. [Pinned EnableMultiTouchMode implementation](https://github.com/jinghuichen/touchMyMac/blob/7c76b645da2ca007c38aeeb3e7613fe2e2b00bee/Core/HIDInterpreter.c#L647)

For MacTouch, make any mode initialization specific to the chosen USB controller, validate the element's advertised type and logical range, expose the result in diagnostics, and retry only within a bounded lifecycle. Do not write guessed report bytes or probe every mode automatically. A successful feature write still requires validation that real touch reports follow. The actual ASUS descriptor will determine whether this path is relevant.

TouchMyMac's input layer at the reviewed revision still keeps its queue, contact-count and hybrid-offset state in globals. Its coordinate workaround handles repeated X/Y values in one parsed element, but does not establish support for every HID array encoding. These are useful isolated cases to turn into fixtures; they are reasons to retain MacTouch's per-device raw-report design. [Pinned input layer](https://github.com/jinghuichen/touchMyMac/blob/7c76b645da2ca007c38aeeb3e7613fe2e2b00bee/Core/HIDInterpreter.c)

## Evidence for ASUS support

The reviewed Touch-Up README lists Iiyama TF3222MC, Iiyama T2336MSC-B2 and 3M C4667PW as tested hardware. TouchMyMac lists LG Smart Monitor Swing and labels other USB HID touchscreens as unvalidated. Neither list confirms the user's ASUS 22-inch monitor. Treat “works on Windows” as a useful discovery clue, not proof of compatibility. [Touch-Up compatibility](https://github.com/shueber/Touch-Up#compatibility), [TouchMyMac tested hardware](https://github.com/jinghuichen/touchMyMac#-tested-hardware)

The mapper project is particularly useful as evidence that a touch collection can be silent while the same panel's mouse-emulation collection sends absolute coordinates. Its README says its investigation used one monitor, and documents limitations in rotation, right-click and multitouch. For an ASUS controller with similar behavior, create a narrowly matched fallback profile after capturing the descriptor and reports; do not broaden matching to every mouse. [Mapper internals and limitations](https://github.com/markstrom/mac-touchscreen-mapper#how-it-works)

## Development tools and next decisions

Use the built-in `hidutil`/IORegistry inspection first. Apple documents HID discovery from Terminal and provides CoreHID examples for device notifications, report I/O and virtual-device testing. CoreHID is a system framework rather than an open-source package to vendor, and its macOS 15 client availability would raise or complicate the macOS 13 baseline. [Apple HID discovery](https://developer.apple.com/documentation/corehid/discoveringhiddevicesfromterminal), [CoreHID communication examples](https://developer.apple.com/documentation/CoreHID/CommunicatingWithHIDDevices), [virtual-device examples](https://developer.apple.com/documentation/corehid/creatingvirtualdevices)

When independent report capture is useful, hidapitester can enumerate devices and retrieve descriptors. On macOS, use its nonexclusive open mode for observation: its default can seize a device. Limit capture to the selected touchscreen rather than unrelated HID devices. No external installer or binary was run for this comparison. [hidapitester command reference](https://github.com/todbot/hidapitester#usage)

For the current app, keep **zero third-party runtime dependencies**. The delivered preview adapts Touch-Up's count/offset approach into a guarded Swift hybrid-frame assembler, with its MIT notice retained and ten new hybrid tests. It also offers a user-invoked standard Device Mode request for the selected controller after checking its advertised Feature element. Neither has been validated on the ASUS hardware yet. Next, inspect the real descriptor and reports, exercise both paths when applicable, and turn captured reports into regression fixtures. Revisit HIDAPI when adding other operating systems or when a demonstrated transport problem makes its maintenance value concrete.
